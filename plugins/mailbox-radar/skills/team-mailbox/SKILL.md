# team-mailbox — Agent 溝通器（universal v1.1）

規約 canonical = 交換區根目錄的 `README_交換區規約.md`。本 skill 內嵌格式與規約衝突時，以規約為準，並告知使用者。

## 腳本與資料位置

- 腳本隨 plugin 發佈，都在 `${CLAUDE_PLUGIN_ROOT}/scripts/`（下稱 S/）。
- 使用者資料在 `~/.claude/team-mailbox/`（刻意放在 plugin 之外，更新 plugin 不會碰到）：
  - `config.md`：名字、交換區路徑（、桌鈴開關）
  - `read.md`：已讀帳
  - `通訊錄.md`：成員名單（email、代稱、姓名、來源、狀態），本 skill 與白名單閘門共用

## Step 0：讀身分與路徑（每次觸發先跑）

1. 讀 `~/.claude/team-mailbox/config.md`（兩段：`名字：<X>`、`交換區：<絕對路徑>`）→ 齊全就用
2. 缺交換區路徑 → 依平台 Glob 定位：
   - Mac：`~/Library/CloudStorage/GoogleDrive-*/{My Drive,我的雲端硬碟}/**/_交換區`
   - Mac（別人分享給你的資料夾捷徑）：`~/Library/CloudStorage/GoogleDrive-*/.shortcut-targets-by-id/*/**/_交換區`
   - Windows：`G:\我的雲端硬碟\...\_交換區`、`C:\Users\*\*Google Drive*\...\_交換區`（磁碟代號依 Drive 桌面版設定，可能不是 G:）
   - 都找不到 → 請使用者在 Drive 網頁對交換區的上層資料夾按右鍵 → 整理 → 新增捷徑到「我的雲端硬碟」，或直接問路徑
3. 缺名字 → 問使用者一次（必須與交換區裡自己的 `收件匣-<名字>` 資料夾後綴完全一致）
4. 把答案寫回 config.md（之後不再問）

## 操作分流

| 使用者意圖 | 走哪段 |
|---|---|
| 傳訊息／留言／問某人 | 發訊息 |
| 查信箱／有沒有人找我／看公告板 | 查信箱 |
| 回覆某則訊息 | 回覆 |
| 對全體廣播 | 發公告 |
| 跨組多人討論 | 議題 |
| 同步／加人／移除／列出成員、查某人 email | 通訊錄 |

## 發訊息

1. **先查對象**：`node S/contacts.mjs check <對方代稱>`。
   - `active: true` → 往下
   - 標記為已離開（left）→ 停下，把 `note` 講給使用者聽，不寄
   - 不在通訊錄 → 跟使用者確認對象是誰；確認後照寄（收件匣資料夾存在就寄得到），並建議之後跑一次「同步通訊錄」
2. 檔名 `訊息_<自己>→<對方>_<主題slug>_<YYYY-MM-DD>.md`，寫進 `收件匣-<對方>/`。寫入前照規約第七條驗證路徑真的在 Drive 掛載上（Mac：`realpath` 落在 `~/Library/CloudStorage/GoogleDrive-*` 下；Windows：路徑在 Drive 串流磁碟或同步資料夾下）；收件匣不存在＝路徑錯，停下來重查，**絕不 `mkdir -p` 補建**
3. 開頭固定 frontmatter：

   ```
   ---
   from: <自己>
   to: <對方>
   type: 訊息 | 請求
   主題: <一句話>
   date: <YYYY-MM-DD>
   需要回應: 是 ／ 否
   期限: <YYYY-MM-DD，選填>
   急迫度: <一般／急，選填>
   ---
   ```

4. **發送前自含 lint（硬規則）**：對方的 Agent 零記憶、沒讀過你的對話——
   - 正文不得出現「如前所述」「上次那個」這類依賴外部脈絡的指涉
   - 涉及檔案 → 附交換區（或共享資料夾）底下的相對路徑
   - 大檔（>50KB）不進交換區 → 放自己名下資料夾，訊息附路徑
   - 自檢一句：「一個陌生 Agent 讀得懂嗎？」不過關就改寫
5. 寫完向使用者回報檔名一句

## 查信箱

掃描範圍 = `收件匣-<自己>/` ＋ `公告板/`，**不全區掃描**。

1. 列出兩處所有 .md，排除已記在本地 `read.md`（已讀帳）者
2. 新訊息逐則向使用者摘要：from／主題／需要回應與期限
3. `需要回應: 是` → 跟使用者確認回覆內容 → 走「回覆」
4. **處理完一定要記帳，用腳本、不要自己編輯檔案**：

   ```
   node S/markread.mjs --note "已回覆" <檔名> [<檔名>...]
   ```

   它會回報實際記了幾筆（`added`）與本來就在帳上的（`skipped`）。**看到回報才算做完**，
   沒看到就是沒記成功。註記自己填得有意義一點（`已回覆`／`已讀過`／`待本人決定`）。

   為什麼不要自己動手寫檔：0.5.x 這一步是一句「把檔名追加進 read.md」的散文指示，
   結果幾乎不會發生——2026-09-10 查到一臺機器的已讀帳停在兩個月前，中間 45 封一筆
   都沒記，雷達因此在每個對話都虛報未讀數。散文指示會被忘記、會寫錯路徑、會寫錯格式，
   而且三種錯法當下都沒有任何跡象。
5. 兩處都沒新東西 → 回報「交換區沒有新訊息」一句，結束

> 0.6.0 起雷達會在開場（或工作途中）**把具體列出來的那幾筆自動記成已讀**，所以你來查信箱時
> 多半已經記過了，第 4 步的 `skipped` 會有東西，那是正常的。自動記的是「已掃到」這個機器事實；
> 你在這裡補的註記才說明「處理結果」，兩者不衝突。

## 回覆

檔名 `回執_<同主題slug>_<自己>_<YYYY-MM-DD>.md`，寫進**原寄件人**的收件匣。
首行 `狀態：<一句話結論>`，正文同樣過自含 lint。frontmatter type: 回執。

## 發公告

檔名 `公告_<主題slug>_<YYYY-MM-DD>.md` → `公告板/`。frontmatter type: 公告、to: 全員。
全體廣播，慎用；需要大家回條時在正文明說（回條 = 回執寫進發佈者收件匣）。

## 議題（跨組多人討論）

- 開題：建 `議題/<YYYY-MM>_<主題slug>/`，首檔 `00_開題_<自己>_<YYYY-MM-DD>.md`
- 回應：同夾內接續編號 `NN_回應_<自己>_<YYYY-MM-DD>.md`（NN = 現有最大編號 +1）
- 一發言一檔，絕不編輯別人的檔（Drive 多人共筆會產生衝突副本）
- 使用者點名某議題 → 讀整夾按編號摘要脈絡再回應

## 通訊錄

通訊錄是成員名單的唯一正本，白名單閘門（收信驗身分）與本 skill（寄信查對象）都讀它。
一行一人、五欄：`email｜代稱｜姓名｜來源｜狀態`。**代稱與姓名是兩回事，不能合併**：代稱是收件匣
資料夾後綴（人工取的，例如 `Alice`、`小A`），姓名是 Google 帳號的顯示名（通常是中文全名），實測多數人對不上。
來源 `drive`＝從 Drive 分享名單同步來的；`manual`＝人工加的。狀態 `active`＝在用；`left`＝已離開（**不刪列**，
這樣離開者的舊訊息閘門仍認得出是誰，而寄信會被擋）。

本段所有範例都是虛構資料（`alice@example.com｜Alice、小A｜王小艾`），照格式換成你們的成員即可。
**不要把真實成員資料寫進任何會被分享的檔案**（skill、README、對話貼圖）。

### 列出

`node S/contacts.mjs list --pretty` → 表格化講給使用者聽。使用者問「<名字> 的 email」也走這條。

### 加人（手動）

`node S/contacts.mjs add <email> <代稱> [--name <姓名>]`。多個代稱用「、」串（`Alice、小A`）。
既有的人再 add 一次＝補代稱或補姓名（不覆寫已填的姓名）；已離開的人再 add＝重新啟用。
手動加的人來源是 manual，之後 Drive 同步不會把他標成離開（人工加、人工移）。

### 移除

`node S/contacts.mjs remove <email 或代稱>` → 狀態改 left，列保留。回報一句「已標記為離開，他的舊訊息仍認得出來」。

### 同步（從 Drive 分享名單）

Drive 只有 session 裡的工具碰得到，所以撈資料的是你，合併規則在腳本裡（`sync` 子命令，可重跑、可 dry-run）。
**用你手上任何能讀 Drive 檔案 permissions 與列目錄的工具**，不同工具的回傳格式不一樣，
**用語意去取值**（「每一位成員的 email 與角色」「每個項目的最後編輯者」），不要對某一種輸出格式寫死解析。

前提：**查詢用的 Google 帳號必須在交換區的分享名單裡（owner 或編輯者）**。不在名單裡的帳號查同一個資料夾，
Drive 回的是「找不到檔案」，不是「沒有權限」——見下方排錯。

1. **找交換區的資料夾 id**：用 Drive 工具以名稱搜尋 `_交換區`（多筆時用路徑或 owner 判斷是哪個）。
2. **成員清單**：對交換區**父層**查一次 permissions，取出每一位成員的 email 與角色。
   子資料夾是繼承的，實測父層與子層回傳逐字相同，**不必逐個子資料夾查**。
   只認「使用者」類的項目；若看到群組（group）、網域（domain）、任何人（anyone）類的分享，個別成員列不出來，
   把這件事告訴使用者、請他改成逐人分享或手動加人。
3. **代稱**：列交換區底下的子資料夾，每個 `收件匣-<代稱>` 去掉前綴就是一個代稱。**代稱的清單以資料夾名為準**
   （檔名裡的代稱寫法可能不一致，不拿檔名定「有哪些代稱」）。
4. **姓名（兩段式，第一段通常拿到一半多）**：permissions 通常拿不到顯示名，改從「最後編輯者」取：
   - 第一段：列子資料夾時帶詳細資訊（detailed），每個資料夾的最後編輯者是「顯示名 ＜email＞」格式，收成 email→姓名。
     這一步只列目錄、不讀任何檔案。實測五個人拿到三個。
   - 第二段：還有成員沒姓名時，才列**自己收件匣**裡的檔案（一樣只列、不讀內容）取最後編輯者。
     **按修改時間新到舊排序，一頁一頁撈，撈到所有成員都有姓名、或撈完為止**——頁數太小會漏掉很久沒寫過東西的人，
     而漏掉的表現（那個人姓名空著）跟「全新交換區還沒人傳訊息」長得一樣，事後分不出來。
     掃自己的收件匣就夠：交換區的訊息與回執都是別人寫進你的收件匣，所以一個人的收件匣會累積到所有同事的署名。
   - 全新的交換區（還沒人傳過訊息）拿不到別人的姓名是正常的，姓名留空、下次同步再補。**姓名不是必填。**
5. **對應代稱與 email——多數人需要人工配對，這是常態不是故障**。代稱多半是英文暱稱或姓氏、顯示名是中文全名，
   字面沒有交集；實測五個人只有一個自動對上。所以先講在前面，不要等看到 unmapped 才嚇到。配對來源按這個順序：
   - **檔名署名對最後編輯者（直接證據，優先）**：第二段列自己收件匣時，每個檔的檔名帶寄件代稱
     （`訊息_<寄件代稱>→…`、`回執_…_<回覆代稱>_…`），同一個檔的最後編輯者就是那個代稱的 email。
     一筆就是一組確鑿的 `代稱 → email`，實測四個人四筆都對得上。把這些寫進 `aliasMap`。
   - **腳本的零歧義自動對應**：代稱等於既有列的代稱／姓名、或等於某人的顯示名。
   - **剩下的問使用者**：回傳的 `unmappedAliases`／`unmappedEmails` 兩邊列給他配對，寫進 `aliasMap` 重跑。**不猜。**
   已有的代稱不會被同步改掉（人工代稱優先）。
6. **寫 facts、跑 sync**：把上面收到的事實寫成 JSON（放暫存目錄，不放交換區、不放 git repo）。**`selfName` 一定要帶**
   （自己的代稱，跟 config.md 的「名字」同一個），健檢靠它認出自己那一列：

   ```json
   {
     "selfName": "Alice",
     "members": [{ "email": "alice@example.com", "role": "owner" }, { "email": "bob@example.com", "role": "writer" }],
     "names": { "alice@example.com": "王小艾", "bob@example.com": "李小波" },
     "folderAliases": ["Alice", "Bob"],
     "aliasMap": { "Bob": "bob@example.com" }
   }
   ```

   先 `node S/contacts.mjs sync --facts <json> --dry-run` 看 `report`（added／left／reactivated／renamed／
   manualNotInDrive／unmapped…），沒問題再去掉 `--dry-run` 寫檔。向使用者摘要變動：誰新加、誰標離開、
   誰對不上。同一份 facts 重跑是冪等的，不會重複加人。
7. **健檢（第一次同步後必看）**：看回傳的兩個欄位——`healthChecked` 必須是 true，然後 `health` 是 null 才算健康；
   `health` 有字就照念給使用者。`healthChecked: false` 代表**檢查根本沒跑**（拿不到自己的代稱），
   不是健康——補 `selfName` 重跑。規則是**自己那一列的姓名一定是滿的**：子資料夾是自己在設定時建的，
   最後編輯者一定有自己。連自己都空，是查詢出了問題（見排錯），**不是「還沒有人傳訊息」**，別把故障誤讀成正常。

### 排錯

- **「找不到檔案」（404 / not found / Requested entity was not found）→ 第一個懷疑綁錯 Google 帳號，不是功能不支援。**
  不在分享名單的帳號查交換區，兩種工具路線都回「找不到」而不是「沒權限」，錯誤訊息會把人引去查路徑或工具。
  先確認工具綁的帳號就是被分享的那個（可指定帳號的工具要指名；綁在連接器上的要看連接器登的是誰）。
- permissions 只回一筆（自己）或空的 → 交換區可能建在共用雲端硬碟（Shared Drive），成員身分掛在雲端硬碟層。
  改查雲端硬碟本身的成員（工具若有 shared drives 相關參數用之），查不到就手動加人。
- 只有檢視權（reader）的帳號能不能列出完整名單，尚未驗證。列不完整時請 owner 或編輯者跑同步，或手動補。
- 姓名全空（含自己）→ 工具沒把顯示名印出來。換一條有「最後編輯者」的列目錄工具，或手動用 `add --name` 補。
- `healthChecked: false`、`health` 說「健檢沒有跑」→ 不是姓名的問題，是檢查沒執行：facts 沒帶 `selfName`、
  而這臺的 config.md 又還沒建（第一次同步常見）。facts 補 `selfName` 重跑；這時的 null 才算數。
- 五個人只對上一個、其餘都在 unmapped → 正常（見步驟 5），用檔名署名對最後編輯者配對，剩的問使用者。

### 從 0.5.x 升上來的人

舊版把成員寫在 config.md 的「白名單：<email> <名字>」行。0.6.0 第一次開對話會自動把那些行轉進通訊錄
（全部當代稱收、來源 manual），config.md 的白名單行不再被讀、可以刪。轉入後建議跑一次「同步通訊錄」補姓名。

## 守則

- **單一 writer**：一檔一作者。別人的檔只讀，不改、不刪、不搬（唯一例外：開題人可把整串已結案訊息移進 封存/，搬移可以、改內容不行）
- **不放機密**：credentials、個資、未去敏素材不進交換區；通訊錄留在本機，不進交換區、不貼進公開文件
- 跨機壓縮檔不用中文檔名（編碼坑）；散檔直放
